# Data-driven gameplay architecture

Gameplay content is described in typed definition records in `Balance.cs` and interpreted by the campaign engine. Presentation code reads the same definitions for menus, so adding an item or courtship entry does not require another UI branch.

They contain no prices, balance coefficients, content names, reward order, or eligibility rules. Imported resource names are translated at boundaries such as `ImportedDilemmaAdapter` and `ImportedSiegeLayouts`; screen code does not interpret raw resource records.

## Strategic save migration boundary

The current schema-1 `StrategicEnemyMovement` stores incompatible reimplementation `World.Locations` indices plus departure/arrival dates. The original system instead persists one of five `0x118`-byte slots with an original 14-property origin, mode, target identity/slot, current and destination coordinates, direction remainder, route identity and waypoint cursor, path-complete state, lord, and three troop counts. These representations are not bijective: a dated schema-1 column has no recoverable original route cursor, person target, sub-cell position, or property-table identity. Schema 2 must therefore be an explicit semantic migration, never an index relabel.

Before enabling exact movement, schema-2 load settles every active schema-1 column in slot order by returning its complete troop total to its still-hostile schema-1 origin garrison when that origin remains valid, otherwise dispersing it, and recording either outcome in the campaign journal. `StrategicSchemaTwoMigration.Prepare` implements and tests that destructive boundary, clears the dated roster, and installs `OriginalStrategicCampaignState`. The replacement owns mutable deep copies of all 14 original properties and 176 original people, five indexed enemy movement slots, six indexed player movement records, selected/distinguished player indices, route-input state, generator accumulator/reactive counter, bounded speed, calendar terrain profile, list heads, strategic camera row/column, and sparse full-dword terrain mutations. Enemy slots persist route identity/direction, waypoint count/index, integer destination/grid coordinates, floating current position/direction remainder, the mode-3 player target slot, path completion, lord, origin, mode, and troop counts. Player records persist their enemy/division-tagged target, fixed inline-route storage, cursor, destination/grid, cooldown, terrain kind, and floating motion state. Validation rejects partial populations, duplicate/missing slots or terrain cells, unknown target tags, non-finite remainder, and incomplete active records. JSON round-trip tests cover every state family and prove definitions are not aliased.

Legacy schema-1 saves that lack `OriginalStrategicState` contain neither a starting-home selector nor strategic camera coordinates. Migration therefore records selector `-1` as an explicit unavailable sentinel and camera `(0,0)` as a deterministic compatibility default; it derives the terrain profile from the saved month and clamps the existing 1-15 UI speed into the exact range. Newly created campaigns now select one of the seven valid `StartingRoutes` through `Campaign.InitializeOriginalStrategicNewGame`, persist the exact bootstrap alongside the still-schema-1 compatibility state, and validate its route during application resource binding. The immutable base terrain remains required resource 292 `icon.jp`; sparse mutations replace the process-global `temp.jap` scratch copy. Camera state is material because inclusive shared-edge pixels resolve by current wrapped draw order: 34 owned-route occurrences at six coordinates differ between opposite camera extremes.

`IOriginalStrategicResources` is the dependency-inversion boundary. Core receives immutable signed route coordinates and camera-projected cells with the complete source dword; Game's `ImportedOriginalStrategicResources` eagerly decodes every distinct executable-selected property/starting route and `icon.jp`, caches forward and reverse order, rejects unknown or malformed assets, and uses `StrategicWorldProjection` for camera-dependent edge ownership. `ConquerorGame` binds the same provider to its initial campaign, every character constructor, and every loaded save. A prepared replacement save is structurally validated during binding, and each active routed slot must match the decoded route's exact point count before the provider becomes observable.

Focus adapter `0x130E4` receives a live record's `(gridX,gridY)` and uses `0x3C6E0` to derive its render camera. With the `20..403` by `7..441` terrain viewport and 80-pixel tile span, the helper first stores `row = (gridX - 2) mod 200` and `column = max(0, gridY - 11)`. `0x130E4` then clamps those intermediate values to row `10..192` and column `2..300` before refreshing terrain, markers, and presentation. `OriginalStrategicMapCamera.FocusOnGridCell` keeps that intentional wrapped-then-clamped edge behavior available to a future host rather than substituting conventional map centering.

Strategic panning is now separately executable-mapped at `0x3D83C-0x3D8B5`: raw map-pointer `x > 628` or `< 8` changes the row once inside `10..192`; raw `y > 474` or `< 8` changes the column once inside `2..300`. A corner can change both axes in source order, and equality is deliberately inert. `OriginalStrategicMapCamera.ApplyMappedEdgeScroll` keeps this state-only rule available to the future strategic screen without treating it as the still-unrecovered screen-to-route click conversion.

The immediately preceding raw map-pointer conversion is now isolated too. `0x122AC` calls `0x640A0`, which maps `(rawX, rawY)` to route space `(rawX + 80 * cameraRow + 40, rawY + 20 * (cameraColumn + 1))` before ordered record hit-testing or route-point insertion. `OriginalStrategicMapPointer.ToMappedRoutePoint` owns that exact integer offset. The source mouse callback and cursor poll store the mouse-service `CX/DX` pair unchanged in the raw globals; they are the same 640-by-480 logical coordinates already supplied by `ConquerorGame.OriginalPoint` after host-window scaling. The mapper intentionally remains separate from that application boundary.

`0x122AC` then resolves the converted point without map-cell quantization. It scans active player records 0 through 5 using `trunc(currentX) + 11, trunc(currentY) - 30, 24, 31`, then hostile movement records 0 through 4 and caller-owned temporary division records 0 through 2 using `trunc(currentX), trunc(currentY) - 20, 40, 40`. Each rectangle uses the source helper's left/top-inclusive, right/bottom-exclusive containment, and the first hit wins before any route insertion. `OriginalStrategicMapHitTesting.HitTest` keeps that visual-input geometry and authored precedence outside the dated campaign model.

`OriginalStrategicMapCommands.DispatchRawPointer` composes that map conversion and hit test with `DispatchPlayerMapCommand`. It leaves only the original popup's accepted/declined target response to the application, so an unconfirmed enemy/division hit is consumed while a player hit selects, and an empty point follows the fixed 20-waypoint route constructor. This is the application boundary for the future strategic screen; it does not give the dated map adapter authority over any original record or temporary division target.

`OriginalStrategicMapTerrainRendering.BuildDraws` is the resource-neutral terrain pass for that screen. It retains `0x3C770`'s source order: the `20..403` by `7..441` map viewport starts at y `-53`, advances every 20 pixels, alternates x `-20`/`20` with the wrapped grid column, advances rows by 80 pixels, and emits partially visible tiles for clipping. `BuildTileDraws` then binds every position to the exact `icon.jp` low-word selector consumed by the original blitter. `OriginalStrategicTerrainPresentation` now binds that plan in the MonoGame host when a schema-2 state is present: it selects `ics` for Spring/Summer, `ica` for Autumn, or `icw` for Winter from the state profile, intersects each source 80-by-80 frame with the logical viewport before scaling, and fails rather than remapping an out-of-range source tile. This presentation binding does not activate the strategic scheduler, pointer dispatcher, or legacy map controls.

The marker frame kernel is distinct from that terrain pass. Initializer `0x12A77-0x12AA5` assigns all six `0x118`-byte player records the common base `0x15EF0(0, 0x13) << 3` at `+0x38`, associates the `icon_men.CSF` handle loaded from object-2 string `+0x4AC` at `+0x110`, and clears the per-record selected field `+0x04`; its paired object-2 string `+0x4BC` is `marker.CSF`. `0x15EF0` dereferences the dynamic `CHARACTR.DAT` table through object-2 `+0xA650`: its second, zero-based field index `0x13` is `COLOR`. Character-options initializer `0x14230` clears row 0's color, then handler `0x145A4-0x1464A` writes 0, 3, or 5 for HAT regions 3 Red, 4 Green, and 5 Blue. The value is dynamic rather than a universal constant. Loader `0x18430` first calls `0x6A190`, a DOS file-attribute probe, with that string address, then opens and decodes the named CSF. `ImportedAnimations` now makes both source-verified CSFs required application assets, while retaining the campaign-shell palette association as Corroborated pending recovery of the load-site palette. For every active player record, `0x12F28` then uses that base plus offset `1/6` for an ordinary unselected/selected record, `5/0` for the distinguished record, and `2/7` for avatar slot 5. Its `0x63EC0` calls explicitly round the branch-selected floating coordinate inputs toward zero before `0x3F0A0` projects them; the avatar branch can use the selected record's paired coordinate. `OriginalStrategicCharacterColor`, the persisted `Player.OriginalStrategicCharacterColor`, and `OriginalStrategicMapMarkerPresentation.FrameBaseForCharacterColor`/`FrameBasesForCharacterColor`/`FrameFor`/`BuildDraws` preserve the confirmed source scale, controls, frame selection, physical-slot order, active filtering, caller-supplied source bases, and pre-projection integer coordinates. `OriginalStrategicMarkerPresentation.BuildBlits` now combines that plan with `TryProjectBlitOrigin`, crops it to the same logical viewport as terrain, and the MonoGame host draws it after the source terrain when that state and the confirmed marker frames are available. It deliberately leaves the palette association Corroborated and does not activate strategic input or scheduling.

The first marker-projection stage is now isolated too. With current camera `(row,column)`, `0x3F0A0` accepts inclusive source `x` from `80*row+40` through that value plus 383, and source `y` from `20*(column+1)` through that value plus 474. It supplies its image blitter origin as `x - (80*row+40) - floor((20*(column+1)+434)/2) + 20`, and `y - 20*(column+1) - imageHeight + 7`; the blitter crops afterwards. `OriginalStrategicMapMarkerProjection.TryProjectBlitOrigin` maps these confirmed bounds and origins, and `OriginalStrategicMarkerPresentation` applies the viewport intersection as the clean-room host counterpart to that downstream blitter clipping.

The second marker pass is independent of player-frame selection. After `0x12F28`, source dispatcher `0x3C2CC` calls `0x3A63C`, which scans five `0x118`-byte movement records at `+0x1AB48` in physical order. Every active record uses its direct `+0x38` frame, toward-zero `+0x5C/+0x60` coordinates, and the `icon_men.CSF` image handle at `+0x110` with the same `0x3F0A0` projection/blitter. Initializer `0x12A4C` clears this frame field; constructor paths `0x3A764` and `0x3AC5C` seed it from `word[object2+0xAE88 + 2 * originProperty] << 3`. Reachable property indices 0--13 therefore select `88,8,16,72,32,56,48,56,64,72,80,88,96,64`. `OriginalStrategicMovementSlot.MarkerFrame` persists that source record field, and the scheduler, `BuildMovementDraws`, `BuildMovementBlits`, and MonoGame player-then-movement draw order preserve it. This proves `marker.CSF` does not supply the second icon pass; its semantics remain Provisional, and palette binding remains Corroborated.

The MonoGame map host now invokes `FocusOnGridCell` at the new-campaign map handoff, using the persisted original home grid before its first terrain/marker draw. On every fixed host update it applies `ApplyMappedEdgeScroll` to the logical 640-by-480 pointer. Primary clicks inside the recovered source viewport dispatch through `OriginalStrategicMapCommands` with three explicitly inactive temporary-division targets: source player-marker selection and route construction are active; enemy/division target clicks are consumed but await the original confirmation-dialogue producer. This deliberately removes the source's processor-dependent panning cadence without inventing acceptance behavior.

`OriginalStrategicHostRuntime` also invokes `Campaign.AdvanceOriginalStrategicPass` exactly once from each MonoGame map update. The host is explicitly configured for a 60 Hz fixed timestep, so the recovered player pass and hostile scheduler use a stable application cadence instead of original caller `0x3C290`'s unrestricted processor throughput. It supplies the three currently unavailable temporary-force targets as inactive. New campaigns retain their source-established fallback target/origin globals and therefore run the hostile scheduler; schema-one migrations retain safe player-record updates but block that scheduler rather than inventing fallback identities. A typed player/enemy contact now opens the source-backed resolver screen and freezes subsequent strategic passes until its automatic or interactive settlement returns.

`OriginalStrategicMovement.AdvanceSchedulerPass` is the complete mutable scheduler boundary around the three-mode motion kernel. It validates replacement state, runs generation before movement, constructs into the first inactive physical slot, then interleaves one handler and its completion outcome for slots 0-4. The shell implements the two exact force initializers, direct grid-person probes, origin-state reinforcement, encounter handoff, and first-nearby-army/player/origin retargeting. `IOriginalStrategicResources.TryGridCell` exposes the cell's auxiliary person identity without reprojection. The original timed branch can read an uninitialized property local after finder failure; the deterministic clean-room path admits that branch only when the current pass supplied a real detection rather than reproducing stale stack memory.

`AdvanceSchedulerPass` derives reactive contact directly from those five player-army targets. It scans properties then player slots in authored order, applies the exact normal/London spatial gates and grid auxiliary-lord identity, mutates property bytes `+0x0D/+0x0E`, and returns one-shot `OriginalStrategicPropertyAlert` values for presentation. The optional injected detection remains only a focused test/integration seam.

`CurrentSaveSchemaVersion` intentionally remains 1 and `Campaign.AdvanceDays` still uses the isolated dated adapter. The six-record player kernel, command constructors, player/enemy contact shell, exact new-game avatar bootstrap, army/avatar membership exchange, and field-record construction/removal are persisted and executable through `OriginalStrategicPlayerCommands`, `AdvancePlayerMovementPass`, `AdvancePlayerPass`, and `Campaign.ToggleArmyMembership`. New custom and pre-generated Game campaigns now initialize that bootstrap through the campaign-owned random source; loaded legacy saves remain selector `-1` until migration. `Campaign.FieldArmy` now constructs its matching original player record when a replacement state is present. New-game initializer `0x110E8` also stores its selected home person at object-2 `+0x1B0C4` and the `0x4389C`-resolved fallback origin at `+0x1B0CC`; `OriginalStrategicCampaignState.SchedulerFallbackTargetPerson` and `SchedulerFallbackOriginProperty` persist those source-owned globals rather than asking a screen to recreate them. `Campaign.AdvanceOriginalStrategicPass` reads those stored globals directly, binds a configured resource provider, external division targets, the live five army records, and executable caller `0x3C290`'s report -> player -> scheduler ordering. It allows the report/player portion of a migrated save to run when the globals are unavailable, but refuses the scheduler rather than fabricating values. Property 7 force support is derived internally as `176 -` the persisted person-list length, matching `0x38A8C`/`0x38B40` and `0x43558`, rather than being guessed at the screen boundary. The caller always performs the report and player pass, then skips only the hostile scheduler while modal global `AEF8` is nonzero; `SchedulerBlockedByModal` exposes that explicit application handoff. Player-contact handoff has a separate `ADC0` active guard at `0x39428`, represented by `PlayerEncounterHandoffActive`; it suppresses a duplicate contact handoff without suppressing player selection or the clear-`AEF8` scheduler. The scheduler receives `AE6C`'s six-record distinguished-player selector (including avatar 5), not the five-army-only pursuit domain. Replacement reports retain the original property name rather than fabricating an incompatible `World.Locations` index. The remaining activation gate is screen input/handoff wiring and fixed-update/load-save integration. Only after that replaces the adapter may migration be invoked from `Campaign.Load` and the schema advance to 2.

Strategic player/enemy contact deliberately remains a typed application handoff, not a call to `FieldBattleSession`. The recovered encounter wrapper `0x35924` reads three player pools through `0x29E58` and three hostile pools from the enemy movement record at `+0x1C/+0x20/+0x24`, then passes all six mutable counters to resolver `0x258FC`. Its exact staging is now modeled by `OriginalStrategicEncounterStaging`: when total forces exceed 60 it applies `floor((total - 60) / 3)` to hostile categories, and player staging first divides by the number of categories at least 20; both use the strict `reduction + 1 < count` guard on every category. The wrapper restores the removed player quantities after resolution but writes resolver-mutated hostile quantities back directly. Its return helper `0x29DE0` increments the selected army's `+0x50` counter, stores the three returned pools at `+0xA4/+0x100/+0x15C`, and clears corresponding transient words at `+0x1B8/+0x214/+0x270`; `Army.OriginalStrategicEncounterCount` and `OriginalStrategicEncounterStates` persist that state without conflating it with force totals. Resolver gate `0x256FC` is an interactive choice dialog; `OriginalStrategicEncounterMenu` preserves its five original regions and jump-table codes in input order: upper-left `30,30,215,185` -> 2, upper-right `400,30,205,200` -> 3, lower-left `25,250,185,185` -> 1, lower-right `375,250,185,185` -> 0, and bottom-centre `220,417,148,38` -> zero-return automatic fallback. Its shared `0x6FF10` selector scans that same order with left/top-inclusive and right/bottom-exclusive containment; the four tactical names remain intentionally unrecovered. When an interactive choice proceeds, `OriginalStrategicInteractiveEncounter` materializes one 52-byte-compatible live unit per staged counter in player swordsman/halberdier/knight order followed by the enemy's same order. It preserves immutable category columns `0/120/240`, lanes `0/360`, type codes `3/7`, and values `10/20/40`; terminal write-back counts only strictly positive strength by that immutable classification. For menu code 0, `0x2904B` places the player prefix at `(60 * floor(i / rows) + 60, 60 * (i % rows) + 30)` where `rows = verticalSpan / 60`; code 1 at `0x290BA` mirrors that x coordinate around `(playerCount / rows) * 60 + 60`. Code 2 at `0x29132` uses the smallest triangular row count `r` with `r * (r + 1) / 2 >= playerCount`, emits row lengths `1..r`, starts at `(45r, verticalSpan / 2)`, and shifts each row by `(-45,-30)`. `ApplyMappedMenuFormation` implements those exact code-0/1/2 player paths, while `ApplyMappedMenuCodeThreeFormation` separately preserves code 3's raw-draw-dependent player/enemy grids. This establishes the six-counter contract for a future exact tactical simulation without replacing it with aggregate `FieldBattleSession` logic. `ResolveAutomatic` compares staged totals plus caller-provided `modifier / 3`, zeros only the staged player counters on a non-winning score, or subtracts three ordered raw-draw remainders modulo the shrinking hostile total from player categories and then restores reserves. `Campaign.AdvanceOriginalStrategicPass` exposes an immutable `OriginalStrategicPlayerEnemyEncounter` snapshot for each accepted contact, carrying the exact player/enemy slots, raw counters, and staged counters before scheduler work; it deliberately has no legacy battle dependency or resolution side effect. `Campaign.ResolveAutomaticOriginalStrategicEncounter` applies that fallback only after verifying the snapshot still matches live records, writes category totals back to the player army and hostile movement slot, and reports either the exact ordinary-field-record removal or the distinguished-player modal requirement. `BATTLE.PCX` and `MEN8.CSF` are loaded as `Encounter.Strategic.Background` and `Encounter.Strategic.Units`, respectively, so the source battlefield and its palette-associated unit frames are verified application dependencies. Their exact layout/frame state dispatch remains intentionally external until the resolver presentation path is recovered. The interactive tactical UI, choice meanings, and conversion to a first-person session remain Provisional; no aggregate battle, garrison, or dated `World.Location` value is an authorized substitute for its six-counter contract.

The preceding initial `3/7` values are headings, not immutable type codes. Constructor `0x28C38` stores them in record `+0x14`; `0x2964C` derives the desired eight-way heading from live source/target coordinates, and `0x296B4` turns that field one octant per pass before entering state `0x28` only when already aimed. State-zero first uses its own source-excluding rectangle-corner acquisition; any resulting or retained target field turns immediately and prevents both later branches that pass. With no target but an outstanding paired destination, it turns once toward that coordinate and then walks vertical before horizontal axes in the same pass. With neither target nor destination, control-code-one sources scan living opposing records in authored order, retain strictly nearer truncated Euclidean distances from `0x7FFF`, and seed the source/candidate destination fields from the chosen record. `AdvanceMappedStateZero` composes this exact precedence from `DetermineMappedHeadingOctant`, `AdvanceMappedTargetHeading`, `AdvanceMappedDestinationOrder`, and `TryAssignMappedAutomaticDestination` against one pre-pass rectangle table. Broader input/presentation scheduling remains pending.

Code 3 at `0x29209-0x29643` is now mapped separately because its exact path needs both viewport dimensions and one raw encounter draw. It splits player swordsmen at `floor(swordsmen / 2)`: its first half uses four-high rows at `x = 60 * (floor(floor(swordsmen / 2) / 4) + 1) + 60 * floor(nonSwordsmen / rows) - 60 * floor(i / 4) + 120`, `y = 60 * (i % 4) + 30`; its latter half retains x and begins at y 480. The non-sword player suffix uses `x = 60 * (floor(floor(swordsmen / 2) / 4) + 1) + 60 * floor(nonSwordsmen / rows) - 60 * floor(i / rows)`, `y = 60 * (i % rows) + 30`. One non-negative raw draw modulo two selects the enemy grid: zero mirrors each column at `horizontalSpan - (60 * floor(i / rows) + 60)`, while one starts at `horizontalSpan - (60 * floor(enemyCount / rows) + 60)` and advances x by 60 per column; both use `60 * (i % rows) + 30` for y. The original's four-entry switch has cases 2/3 which cannot follow its modulo-two remainder, so `ApplyMappedMenuCodeThreeFormation` preserves only the two reachable layouts rather than recreating dead paths. This supersedes the earlier code-3 limitation above; the existing three-layout API remains intentionally narrow because it has no source for the required width or draw.

The first exact interactive-loop record mutation is also mapped. At `0x26B88`, each positive-strength record produces an 8-byte render rectangle from `(+0x04 - 15, +0x08 - 20, 25, 30)` while non-positive records produce zero rectangles, then the loop calls `0x264F8` and returns immediately on its nonzero result. In its completed death state `+0x1C = 0x50`, when `(prior + 1) % 5 = 4`, the loop decrements the matching side total, writes `+0x20 = 0`, and changes category `+0x00` from knight `0xF0` to halberdier `0x78`. Thus category values are initial classification values, not permanently immutable live fields; strict-positive survivor write-back remains unaffected. `OriginalStrategicInteractiveEncounterSession.AdvanceMappedTacticalPass` retains one rectangle snapshot and visits the table in source order: it advances death state, applies state-`0x28`'s zero-offset probe/contact, and then enters state zero only when that result has cleared the current state. The original input and processor-dependent timing wrapper remain deliberately external.

Interactive resolver loop `0x26B88` is timed by helper `0x18420`, which returns interrupt counter `A688` shifted left two. Timer callback `0x183C1` increments that counter; the loop skips a tactical pass while `currentClock <= lastSample + 0xC8`, then samples the clock again and replaces `lastSample` before visiting units. It consequently accepts the strict post-200-timer-unit boundary once and does not run catch-up passes after a late frame. Because the interrupt frequency is not recovered, `OriginalStrategicInteractiveEncounterTiming` represents the invariant against a monotonic absolute `TimeSpan` with an explicit host cadence. Its default 200-ms compatibility value is a deterministic policy rather than an original-duration claim. `19C7C` initially skips tactical work; the first control stores zero there and sets `19C8C`, enabling passes. Only later hits with `19C8C` set display the retreat dialog. `AdvanceMappedFrame` preserves that activation, later confirmation, enemy-first/player-second terminal order, and deterministic cadence without reproducing processor dependence.

The interactive neighbor path now has its exact geometry primitive. Selector `0x6FF10` scans the temporary eight-byte rectangle array in increasing table order, returns its first hit as a one-based index (zero for no hit), and delegates to `0x64164`'s `left <= x < left + width`, `top <= y < top + height` predicate. The `0x26B88` loop emits `(PositionX - 15, PositionY - 20, 25, 30)` only for positive-strength units and a zero rectangle otherwise. `OriginalStrategicInteractiveEncounterGeometry` preserves this ordered, half-open selector, `0x28408`'s source-excluding transformed-corner helper including its dead-first-hit asymmetry, and state-zero's distinct opposing-only corner acquisition. `AdvanceMappedDestinationOrder` uses that retained start-of-pass table for the verified state-zero destination step; broader state-machine scheduling remains intentionally unmapped rather than approximated.

Before dispatching encounter controls, `0x264F8` applies viewport scrolling in four source-ordered checks. A pointer at most five pixels from the left/top decrements its respective offset by 10 only when it is positive; a pointer at least five pixels from the right/bottom increments it by 10 only when `contentWidth - viewportWidth - 10 > horizontalOffset` or `contentHeight - viewportHeight - 50 > verticalOffset`. The strict inequalities and distinct 50-pixel lower reserve are material compatibility facts, not generic camera clamping. `OriginalStrategicInteractiveEncounterViewport` exposes those offsets and `ApplyMappedEdgeScroll`; the input event codes and associated UI labels remain deliberately unmapped.

The live interactive unit model now retains the constructor's remaining state fields from `0x28C38`: `+0x0C/+0x10 = -1`, `+0x18/+0x1C = 0`, `+0x28 = 0/1` for player/enemy, and `+0x30 = -1`. `+0x0C/+0x10` are later written together by the control path, `+0x18` is a modulo-five phase counter, `+0x1C` reaches the confirmed death state `0x50`, and `+0x30` is later consumed as a table-relative unit index. `+0x28` is intentionally exposed as `ControlCode`, not falsely named a permanent side flag, because the control path overwrites it. `OriginalStrategicInteractiveEncounterUnit` preserves these fields with source-offset comments and initialization tests while their remaining semantics stay Provisional.

The first player-control operation is now executable rather than inferred from a generic tactical model. For each selected unit index, `0x26A7F-0x26B64` clears `ControlCode`, writes `AuxiliaryX = localX + horizontalOffset` and `AuxiliaryY = clampedLocalY + verticalOffset`, where local Y is first raised to 45 and then lowered to `verticalSpan - 85`; X is not clamped. `ApplyMappedDestinationOrder` preserves the original selected-list order, paired destination writes, and this asymmetric boundary rule. `ApplyMappedInput` dispatches recovered codes 6/7 to it, while retaining caller-owned event production and later state evaluation.

Two neighboring control mutations are also literal-mapped but deliberately unnamed as gameplay commands. `0x26918-0x26966` writes `ControlCode = 1` to every index already in the selected list, with no fresh side or strength check; `0x26968-0x26999` writes the same value to every positive-strength record across both lanes. `SetMappedControlCodeOneForSelectedRecords` and `SetMappedControlCodeOneForLivingRecords` preserve their different filters. The outer raw dispatcher reaches these exact branches only through `0x61` and `0x41` respectively, exposed by `ApplyMappedRawControlCodeOneInput`; the source display regions, host event producer, and meaning of control codes zero and one remain Provisional.

The first control strip rectangle is no longer unnamed: its initial hit enables tactical passes by writing `19C7C=0` and `19C8C=1`; only a later hit invokes the object-2 prompt `Do you want to retreat?`, whose accepted reply ends the resolver. `ActivateMappedFirstControl` and `ResolveMappedRetreatConfirmation` retain this Confirmed activation/terminal route without inventing the host's affirmative/negative event mechanics. The session also exposes the three mapped category-selection loops separately from unrecovered key-event production. `AppendMappedPlayerCategorySelection` appends living player swordsmen, knights, or halberdiers to the current byte-list in authored materialization order and preserves prior selections. `RouteMappedCategorySelectionInputCode` and the session's raw-input facade additionally preserve the outer dispatcher's exact `0x48/0x68`, `0x4B/0x6B`, and `0x53/0x73` routes to swordsmen, knights, and halberdiers. The implementation does not invent selection clearing, an arbitrary capacity, a visual-order sort, or an operating-system key producer.

The state-`0x28` contact's resolved-record arithmetic uses the mapped zero-offset neighborhood probe. At phase two, `0x26DCB-0x270B4` subtracts raw remainder modulo 10 for knight→halberdier, swordsman→knight, and halberdier→swordsman contacts, or modulo 7 otherwise; targets in the enemy lane also receive the resolver's `playerScoreModifier / 3`. Target health strictly between zero and 20 enters state `0x50` with phase zero; a non-positive target clears the attacker's target/state and clears its auxiliary pair only when the attacker has control code one. `OriginalStrategicInteractiveEncounterCombat` and `AdvanceMappedTacticalPass` preserve these record effects, the source's `19C98` lane filter, and re-entry into state zero without assigning unverified buttons or timing.

Immediately before that arithmetic, `0x26D4B-0x26DC5` calls `0x28408` with zero X/Y offsets and treats probe results zero and one as a contact loss: it clears state and target, then clears auxiliary coordinates only for control code one. Every other result advances the phase counter modulo five, and only the resulting phase two may resolve damage. `ApplyMappedContactProbeResult` and the fixed pass preserve that raw return-code boundary and carry a contact-loss record into the immediately following state-zero branch.

## Validation

The executable specifications reject duplicate equipment and courtship names, duplicate win rewards, mismatched building keys, and dragon requirements that cannot be earned from a defined reward ladder. Full campaign behavior tests then exercise the same generic interpreters used by the game.

## Runtime paths and packages

`GamePathResolver` keeps distributable content and writable player state separate. Imported `UserContent` is selected explicitly by `--user-content`, then `RECONQUEROR_USER_CONTENT`, an adjacent or package-root directory, a development checkout, and finally the platform's per-user application-data directory. Saves and settings always use the per-user `ReConquerorAD1086` state root, so an installed game never assumes its program directory is writable. Windows Inno Setup, Linux Debian, and macOS package builders all consume the same verified, self-contained portable publish layout.

`Directory.Build.targets` enforces a 1,000-line ceiling for every compiled C# source file in every project, making oversized responsibilities a local-build, test, CI, and release failure. `ConquerorGame` is divided into lifecycle, campaign-input, general-presentation, and location/combat-presentation partials; the large resource regression suite is divided along the same responsibility boundaries. The limit can be lowered with `MaximumSourceFileLines` for validation; disabling it requires the explicit `DisableSourceFileLineLimit=true` MSBuild property.

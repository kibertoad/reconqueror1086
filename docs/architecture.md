# Data-driven gameplay architecture

Gameplay content is described in typed definition records in `Balance.cs` and interpreted by the campaign engine. Presentation code reads the same definitions for menus, so adding an item or courtship entry does not require another UI branch.

| `OriginalStrategicCampaignState` / `StrategicSchemaTwoMigration` | mutable 14-property/176-person copies, five enemy slots, six player records, exact cursors/sub-cell/route-input state, generator/speed/profile/camera state, sparse full-dword terrain mutations, and deterministic schema-1 settlement | dormant schema-2 replacement boundary pending live binding and game-loop integration |

The remaining switches in the core are state adapters: they map typed equipment slots, building kinds, and dilemma attributes to serialized player fields. They contain no prices, balance coefficients, content names, reward order, or eligibility rules. Imported resource names are translated at boundaries such as `ImportedDilemmaAdapter` and `ImportedSiegeLayouts`; screen code does not interpret raw resource records.

## Strategic save migration boundary

The current schema-1 `StrategicEnemyMovement` stores incompatible reimplementation `World.Locations` indices plus departure/arrival dates. The original system instead persists five movement records (FMT-STRATEGY-001) with a property origin, mode, target identity/slot, current and destination coordinates, direction remainder, route identity and waypoint cursor, path-complete state, lord, and three troop counts. These representations are not bijective: a dated schema-1 column has no recoverable original route cursor, person target, sub-cell position, or property-table identity. Schema 2 must therefore be an explicit semantic migration, never an index relabel.

Before enabling exact movement, schema-2 load settles every active schema-1 column in slot order by returning its complete troop total to its still-hostile schema-1 origin garrison when that origin remains valid, otherwise dispersing it, and recording either outcome in the campaign journal. `StrategicSchemaTwoMigration.Prepare` implements and tests that destructive boundary, clears the dated roster, and installs `OriginalStrategicCampaignState` only when a save has none. Schema-one saves written after source-shaped new-game bootstrap can contain both the exact state and the old dated roster; migration validates and preserves that exact state while settling only the incompatible columns, rather than discarding source route/camera/person state. The replacement owns mutable deep copies of all 14 original properties and 176 original people, five indexed enemy movement slots, six indexed player movement records, selected/distinguished player indices, route-input state, generator accumulator/reactive counter, bounded speed, calendar terrain profile, list heads, strategic camera row/column, and sparse full-dword terrain mutations. Enemy slots persist route identity/direction, waypoint count/index, integer destination/grid coordinates, floating current position/direction remainder, the mode-3 player target slot, path completion, lord, origin, mode, and troop counts. Player records persist their enemy/division-tagged target, fixed inline-route storage, cursor, destination/grid, cooldown, terrain kind, and floating motion state. Validation rejects partial populations, duplicate/missing slots or terrain cells, unknown target tags, non-finite remainder, and incomplete active records. JSON round-trip tests cover every state family and prove definitions are not aliased.

Legacy schema-1 saves that lack `OriginalStrategicState` contain neither a starting-home selector nor strategic camera coordinates. Migration therefore records selector `-1` as an explicit unavailable sentinel and camera `(0,0)` as a deterministic compatibility default; it derives the terrain profile from the saved month and clamps the existing 1-15 UI speed into the exact range. Newly created campaigns now select one of the seven valid `StartingRoutes` through `Campaign.InitializeOriginalStrategicNewGame`, persist the exact bootstrap alongside the still-schema-1 compatibility state, and validate its route during application resource binding. The immutable base terrain remains required resource 292 `icon.jp`; sparse mutations replace the process-global `temp.jap` scratch copy. Camera state is material because the cell a point finds depends on the camera (RULE-STRATEGY-014).

`IOriginalStrategicResources` is the dependency-inversion boundary. Core receives immutable signed route coordinates and camera-projected cells with the complete source dword; Game's `ImportedOriginalStrategicResources` eagerly decodes every distinct executable-selected property/starting route and `icon.jp`, caches forward and reverse order, rejects unknown or malformed assets, and uses `StrategicWorldProjection` for camera-dependent edge ownership. `ConquerorGame` binds the same provider to its initial campaign, every character constructor, and every loaded save. A prepared replacement save is structurally validated during binding, and each active routed slot must match the decoded route's exact point count before the provider becomes observable.

`OriginalStrategicMapCamera.FocusOnGridCell` implements `focus_on` (RULE-STRATEGY-014) for a future host rather than substituting conventional map centering.

`OriginalStrategicMapCamera.ApplyMappedEdgeScroll` implements edge panning (RULE-STRATEGY-014) as a state-only operation. It moves both axes in one call and leaves the hostile pass running, where the rule moves one axis and holds the hostile pass back.

`OriginalStrategicMapPointer.ToMappedRoutePoint` converts the pointer to route space as RULE-STRATEGY-013 does. Its input is the same 640-by-480 logical coordinates `ConquerorGame.OriginalPoint` supplies after host-window scaling; the mapper remains separate from that application boundary.

`OriginalStrategicMapHitTesting.HitTest` keeps the hit rectangles and precedence of RULE-STRATEGY-013 outside the dated campaign model.

`OriginalStrategicMapCommands.DispatchRawPointer` composes that map conversion and hit test with `DispatchPlayerMapCommand`. Target hits expose `RequiresTargetConfirmation` for the attack prompt of RULE-STRATEGY-013. The host preserves that synchronous boundary with an explicit pending state, repeats the saved raw pointer only on its Enter acceptance, and consumes Escape as decline; those key bindings and wording are Provisional host policy. Thus an unconfirmed target hit is consumed while a player hit selects and an empty point follows the fixed 20-waypoint route constructor. The core consumes the raid requests of RULE-STRATEGY-019 after each full strategic pass to create the two raids, but their visible labels and availability remain outside the dated map adapter's authority.

`OriginalStrategicMapTerrainRendering.BuildDraws` is the resource-neutral terrain pass for that screen. It keeps the order of `draw_terrain` (RULE-STRATEGY-015), and `BuildTileDraws` binds every position to its `icon.jp` low word. `OriginalStrategicTerrainPresentation` now binds that plan in the MonoGame host when a schema-2 state is present: it selects the season's atlas from the state profile (RULE-STRATEGY-009), intersects each source 80-by-80 frame with the logical viewport before scaling, and fails rather than remapping an out-of-range source tile. This presentation binding does not activate the strategic scheduler, pointer dispatcher, or legacy map controls.

The marker frames follow RULE-STRATEGY-015. `ImportedAnimations` makes `icon_men.CSF` and `marker.CSF` required application assets, and draws them with the campaign-shell palette; which palette the original installs for them is not traced (`parity/STRATEGY.md`). `OriginalStrategicCharacterColor`, the persisted `Player.OriginalStrategicCharacterColor`, and `OriginalStrategicMapMarkerPresentation.FrameBaseForCharacterColor`/`FrameBasesForCharacterColor`/`FrameFor`/`BuildDraws` preserve the frame base and selection, physical-slot order, active filtering, caller-supplied source bases, and pre-projection integer coordinates. `OriginalStrategicMarkerPresentation.BuildBlits` now combines that plan with `TryProjectBlitOrigin`, crops it to the same logical viewport as terrain, and the MonoGame host draws it after the source terrain when that state and the confirmed marker frames are available. It deliberately leaves the palette association Corroborated and does not activate strategic input or scheduling.

`OriginalStrategicMapMarkerProjection.TryProjectBlitOrigin` maps the bounds and origin of `draw_marker` (RULE-STRATEGY-015), and `OriginalStrategicMarkerPresentation` applies the viewport intersection as the host counterpart to the blitter's clipping.

`OriginalStrategicMovementSlot.MarkerFrame` persists each hostile record's frame (RULE-STRATEGY-004, RULE-STRATEGY-015), and the scheduler, `BuildMovementDraws`, `BuildMovementBlits`, and the MonoGame player-then-movement draw order preserve it.

The MonoGame map host now invokes `FocusOnGridCell` at the new-campaign map handoff, using the persisted original home grid before its first terrain/marker draw. On every fixed host update it applies `ApplyMappedEdgeScroll` to the logical 640-by-480 pointer. Primary clicks inside the recovered source viewport dispatch through `OriginalStrategicMapCommands` with the three persisted temporary-force records in source slot order: source player-marker selection and route construction are active, and enemy/division target clicks enter the shared confirmation boundary. The host repeats a saved raw click only after its explicit confirmation policy accepts it. This deliberately removes the source's processor-dependent panning cadence without fabricating the original dialog's wording or physical controls.

`OriginalStrategicHostRuntime` also invokes `Campaign.AdvanceOriginalStrategicPass` exactly once from each MonoGame map update. The host is explicitly configured for a 60 Hz fixed timestep, so recovered temporary patrol, player, and hostile work use a stable application cadence instead of the original's unrestricted processor throughput. The campaign first advances initialized slot-1/2 temporary routes in physical order, then applies the order expiry of RULE-STRATEGY-017 before projecting the resulting three persisted records into the player-command target array; this preserves the original temporary -> report -> player -> scheduler relationship without a stale host snapshot. New campaigns retain their source-established fallback target/origin globals and therefore run the hostile scheduler; schema-one migrations retain safe player-record updates but block that scheduler rather than inventing fallback identities. A typed player/enemy contact now opens the source-backed resolver screen and freezes subsequent strategic passes until its automatic or interactive settlement returns. The yearly brigand order and the orders from the king (RULE-STRATEGY-016) are not created.

The map's Plus/Minus controls now call `Campaign.AdjustStrategicSpeed`, changing the live `OriginalStrategicCampaignState.SpeedMultiplier` within 1 to 15 (RULE-STRATEGY-009) and mirroring it into schema-1 `DaySpeed` while the dated adapter remains. `Campaign.AdvanceDays` reselects `TerrainProfile` at each month boundary from the month (RULE-STRATEGY-009), so the imported seasonal atlas and source movement speed table advance together. The calendar-boundary update is a host policy; the original sets the season at map setup and in the map dispatcher. This binding does not make the dated travel, spy, and enemy-movement adapter source-equivalent; schema 2 stays gated on those remaining migrations.

`ImportedMovies`, `OriginalStrategicTerrainPresentation.TransitionMovieRoleFor`/`TransitionMovieBounds`, and `ConquerorGame.PlayPendingStrategicSeason` bind the season movies of RULE-STRATEGY-009, whose 192-by-268 dimensions the Smacker inventory gives, to a dated profile change. The host queues a movie at manual calendar advancement or travel and plays it on map reentry; that trigger timing is **Provisional** because the source's complete map reentry calendar path is not yet mapped. `ResourceAndDefinitionTests.StrategicCalendar` pins the profile-to-movie mapping and source placement.

The dragon's lair ends the player pass before later player records or the hostile pass run (RULE-STRATEGY-010). The host's optional Escape withdrawal leaves a live record in that region, so `ConquerorGame.UpdateOriginalStrategicMapRuntime` keeps a transient suppression latch until that record leaves. It forwards `SuppressDragonEntry` to the player pass only during this host-only interval, allowing the later records and scheduler to continue without opening another battle. The source-backed, unsuppressed entry still returns early and defers scheduler work while the asynchronous battle opens.

`OriginalStrategicMovement.AdvanceSchedulerPass` is the complete mutable scheduler boundary around the three-mode motion kernel. It validates replacement state, runs generation before movement, constructs into the first inactive physical slot, then interleaves one handler and its completion outcome for slots 0-4. The shell implements the two exact force initializers, direct grid-person probes, origin-state reinforcement, encounter handoff, and first-nearby-army/player/origin retargeting. `IOriginalStrategicResources.TryGridCell` exposes the cell's auxiliary person identity without reprojection. The rare timed branch of RULE-STRATEGY-003 tests a stale property (BUG-STRATEGY-001); the rebuild admits that branch only when the current pass supplied a real detection.

`AdvanceSchedulerPass` derives reactive contact directly from those five player-army targets. It scans properties then player slots in authored order, applies the gates of `find_reaction` (RULE-STRATEGY-003), sets `alerted` and `approached`, and returns one-shot `OriginalStrategicPropertyAlert` values for presentation. The optional injected detection remains only a focused test/integration seam.

`CurrentSaveSchemaVersion` intentionally remains 1 and `Campaign.AdvanceDays` still uses the isolated dated adapter. The six-record player kernel, command constructors, player/enemy contact shell, exact new-game avatar bootstrap, army/avatar membership exchange, and field-record construction/removal are persisted and executable through `OriginalStrategicPlayerCommands`, `AdvancePlayerMovementPass`, `AdvancePlayerPass`, and `Campaign.ToggleArmyMembership`. New custom and pre-generated Game campaigns now initialize that bootstrap through the campaign-owned random source; loaded legacy saves remain selector `-1` until migration. `Campaign.FieldArmy` now constructs its matching original player record when a replacement state is present. A new game also stores `fallback_person` and `fallback_origin` (RULE-STRATEGY-012); `OriginalStrategicCampaignState.SchedulerFallbackTargetPerson` and `SchedulerFallbackOriginProperty` persist those source-owned globals rather than asking a screen to recreate them. `Campaign.AdvanceOriginalStrategicPass` reads those stored globals directly, binds a configured resource provider, external division targets, the live five army records, and the report -> player -> hostile-pass order of RULE-STRATEGY-001. It allows the report/player portion of a migrated save to run when the globals are unavailable, but refuses the scheduler rather than fabricating values. Property 7's household is derived internally from the persisted person list (RULE-STRATEGY-005). `SchedulerBlockedByModal` stands for `map_busy` (RULE-STRATEGY-001). `PlayerEncounterHandoffActive` stands for the encounter's `map_session_over` guard (RULE-STRATEGY-011); it suppresses a duplicate contact handoff without suppressing player selection or the hostile pass. The scheduler receives `ridden_force`, which can be 5. Replacement reports retain the original property name rather than fabricating an incompatible `World.Locations` index. The remaining activation gate is screen input/handoff wiring and fixed-update/load-save integration. Only after that replaces the adapter may migration be invoked from `Campaign.Load` and the schema advance to 2.

The strategic encounter screen follows the BATTLE rules, and `parity/BATTLE.md` lists where it differs. `Campaign.AdvanceOriginalStrategicPass` exposes an immutable `OriginalStrategicPlayerEnemyEncounter` snapshot for each accepted contact, and the settlement methods of `Campaign` verify that the snapshot still matches the live records before they write counts back. `OriginalStrategicEncounterMenu` holds the choice regions, `OriginalStrategicEncounterStaging.ResolveAutomatic` the automatic battle, and `OriginalStrategicInteractiveEncounterSession` composes the unit table, formations, selection, input routes, unit updates, lane totals and timing from `OriginalStrategicInteractiveEncounter` and its `Geometry`, `Combat`, `Timing`, `Viewport` and `Presentation` parts. The session materializes only the staged forces; `Campaign.ResolveInteractiveOriginalStrategicEncounter` restores the reserves at settlement. `FieldBattleSession` plays no part in it.

## Validation

The executable specifications reject duplicate equipment and courtship names, duplicate win rewards, mismatched building keys, and dragon score items that cannot be earned from a defined reward ladder. Full campaign behavior tests then exercise the same generic interpreters used by the game.

## Runtime paths and packages

`GamePathResolver` keeps distributable content and writable player state separate. Imported `UserContent` is selected explicitly by `--user-content`, then `RECONQUEROR_USER_CONTENT`, an adjacent or package-root directory, a development checkout, and finally the platform's per-user application-data directory. Saves and settings always use the per-user `ReConquerorAD1086` state root, so an installed game never assumes its program directory is writable. Windows Inno Setup, Linux Debian, and macOS package builders all consume the same verified, self-contained portable publish layout.

`Directory.Build.targets` enforces a 1,000-line ceiling for every compiled C# source file in every project, making oversized responsibilities a local-build, test, CI, and release failure. `ConquerorGame` is divided into lifecycle, campaign-input, general-presentation, and location/combat-presentation partials; the large resource regression suite is divided along the same responsibility boundaries. The limit can be lowered with `MaximumSourceFileLines` for validation; disabling it requires the explicit `DisableSourceFileLineLimit=true` MSBuild property.
